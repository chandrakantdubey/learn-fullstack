# SQLAlchemy

**Role:** Primary | **Layer:** Python data access

## What it is

SQLAlchemy is Python's database toolkit and ORM. Its Core expression system models SQL explicitly; its ORM maps database rows and relationships to Python objects. Both use engines, connections, transactions and pools underneath.

## Mental model

```text
application service
  → transaction / unit of work
  → SQLAlchemy session or connection
  → SQL expression / ORM
  → connection pool
  → PostgreSQL
```

The database remains the authority for relational constraints and transaction semantics. SQLAlchemy is an access layer, not a substitute for understanding SQL.

## Core vs ORM

Use Core when SQL shape and explicit database behavior matter. Use the ORM when object mapping and relationship navigation improve application clarity. Production systems commonly use both rather than treating them as mutually exclusive.

Always inspect the SQL generated by important queries. An ORM abstraction does not remove database cost.

## Sessions and transactions

Treat a transaction as an application boundary, not as a global request-wide default. Keep transactions short and explicit around mutations that must commit atomically.

Do not hold a transaction open while waiting on slow external APIs, user interaction, or unrelated work.

A session is not a magical cache or a safe global singleton. Define lifecycle and concurrency ownership explicitly.

## Query performance

Watch for:

- N+1 relationship loads
- accidental lazy loading
- unbounded result sets
- missing indexes
- excessive columns
- long transactions
- connection pool exhaustion
- inefficient pagination

Use eager loading intentionally, select only required fields where useful, inspect query plans in PostgreSQL, and measure query count/latency.

## Concurrency and failures

PostgreSQL can surface serialization failures, deadlocks and connection failures under real concurrency. Retry only operations that are safe to retry, at the appropriate transaction boundary, with bounded backoff.

Do not retry arbitrary business mutations after an unknown commit outcome without an idempotency strategy.

## Pooling

Pool size is a capacity decision. Too many connections can overload PostgreSQL; too few can queue requests unnecessarily. Size pools across all application instances and account for other database clients.

Monitor pool checkout latency, active/idle connections and database saturation.

## Migrations

Use Alembic for schema evolution. Migrations should be reviewed as production operations: lock duration, table size, backfill cost, compatibility during rolling deploys, rollback strategy and index creation behavior all matter.

Prefer expand/contract changes when old and new application versions may coexist.

## Production checklist

- explicit transaction boundaries
- controlled session lifecycle
- query plans inspected for hot paths
- N+1 detection
- bounded result sets
- indexes matched to access patterns
- pool sizing based on total deployment capacity
- serialization/deadlock handling
- migration compatibility reviewed
- integration tests against PostgreSQL

## Failure modes

Watch for session misuse across concurrent tasks, long transactions, pool exhaustion, ORM waterfalls, implicit lazy loads, hidden queries during serialization, and treating database exceptions as generic application errors.

## Testing

Use integration tests against a real PostgreSQL instance for transactions, constraints, locking, migrations and query behavior. Unit-test application logic separately. Test concurrent operations for invariants that depend on database isolation or uniqueness constraints.
